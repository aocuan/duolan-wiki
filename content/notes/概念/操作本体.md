# 操作本体

操作本体（operational ontology）指的是把「组织里有什么、怎么连、如何合法改变、谁能看见与执行」放进同一套模型，供人和 agent 共同使用。它不是检索加速层，也不是一份学术 OWL 文件。

公开讨论里，最常被当作参照的是 Palantir Foundry / AIP 那一套说法。官方概述见 [Ontology overview](https://www.palantir.com/docs/foundry/ontology/overview)。

## 四件套

可以先记住四件事：

1. **对象（Object）**：一类真实世界实体或事件的类型，以及具体实例。例如「客户」「订单」「设备」。类型规定主键和必要属性；一百份订单仍属于同一个「订单」类型。
2. **链接（Link）**：对象之间被明确声明的业务关系，不是数据库里顺手留下的外键。链接回答「为什么这两个对象连在一起」。
3. **动作（Action）**：人和 agent 改变业务状态的合法入口。谁能把订单从「待确认」改成「已确认」，必须走预先定义的动作，而不是直接改库。自动化的数据转换通常不叫动作，而叫流水线或函数。
4. **权限（Security）**：谁能看见哪些对象、谁能执行哪些动作，并且留下审计。模型答对了，不等于机构可以执行。模型生成的答案也要继承所用数据的权限，见 [[输出权限继承]]。

更完整的产品表述还会把属性、接口、函数算进去。入门时先抓住「语义（对象和链接）+ 动能（动作）+ 权限」就够。

## 和相近概念的差别

- **学术 OWL / 语义网**：强调类、属性、公理和推理，通常没有「动作写回业务系统」这一格。
- **知识图谱 / GraphRAG**：实体和关系为主，服务检索与问答；动作层通常很弱或没有。知识库解决的是「找得到、答得对」，操作本体还要解决「改得合法」。见 [[企业知识库开源选型]]。
- **语义层 / 指标层**：在分析场景里统一「收入怎么算」，主要仍是读，不负责受控写回。

## 何时值得立项，何时不必

值得认真做的信号：业务状态必须受控地改变，而且人和 agent 要共用同一套对象和许可动作。

先不必立项的信号：只是想做文档问答；主数据还对不上，对象都切不清；写回没有唯一入口，权限也落实不到动作上。那种情况下，先把数据和权限理清，比先画一张漂亮的概念图更重要。
