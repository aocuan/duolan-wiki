# 前端设计 Skills 怎么串

这类 skill 要解决的是同一件事：默认大模型做出来的界面常常长得一样。训练数据里重复出现同一批模板，于是容易出现相近的字体、渐变、卡片套卡片和过量动效。设计 skill 的作用是给 agent 一套可调用的设计动词，再配上明确的「不要做什么」。

## 结论

不要把它们理解成「再装一个就能自动变美」的单品，而要按阶段串：

1. **动手前**：先锁定受众、用途和品牌气质，再动视觉。不要让模型从代码里猜品牌。
2. **搭界面**：用官方或项目自己的组件与设计系统 skill，把圆角、间距、密度写成可检查的约定。
3. **打磨和评审**：用「更大胆 / 更安静 / 对齐系统 / 加动效」这类互斥或可串的动词，一次只强化一个方向；再用审计和反模式清单抓住套模板的痕迹。
4. **记偏好**：把反复出现的纠正写成规则，能做成检查脚本的，就不要每次口头提醒。

## 常见来源怎么分工

- **Anthropic 官方 `frontend-design`**：单个 skill，原则短、范围泛，适合作为最小起点。
- **[impeccable](https://github.com/pbakaus/impeccable)**（Paul Bakaus，Apache-2.0，约 11.2 万星，截至 2026-11-17，太平洋时间）：在官方思路上做了扩展，提供更密的反模式、领域参考和一组转向命令。官网是 [impeccable.style](https://impeccable.style)。推荐的短路径是先审计、再整理、再打磨；改界面之前要先收集设计上下文，而不是直接从代码里推断。
- **Emil Kowalski 的一组 skill**：更偏交互、动效和「小而具体的规则」，刻意不锁定某种视觉风格。文档按「动手前、搭界面、打磨评审、看整个应用」排列，见 [aiforui.dev/skills](https://aiforui.dev/skills)。
- **组件库官方 skill**（例如 shadcn 一类）：负责把设计标记映射到主题和组件变体，解决的是「和现有系统对齐」，不是单独发明一套审美。

这些东西可以叠用。讲解图、走查、无障碍或行为库 skill 通常不管配色，正好补在打磨阶段。

## 使用上的硬约束

- 先有设计上下文，再改界面。项目里如果已经有设计说明，不要悄悄覆盖。
- 规则写小、写具体，能变成检查项的就写成检查项。
- 不同模型的界面毛病不一样，一个 skill 换到另一个模型上，效果可能明显不同。
- 星标高的设计 skill 更新很快，安装来源只认官方仓库，不要下来路不明的压缩包。这条和 [[薄技能与重框架]] 里的安全提醒是同一类问题。
